# Design decisions

This document records the significant design decisions made while building `aur-pipelines`, and — more importantly — the
reasoning behind them. It complements the `.kiro/steering/` files (which describe _what_ the conventions are) by
capturing _why_ they are what they are, so future changes can be made with the original trade-offs in mind.

Each entry notes the decision, the context, and the rationale. Where a decision could reasonably be revisited, that is
called out.

## 1. Programmatic Concourse pipeline model (not templates)

**Decision.** Pipelines are built from typed Go structs in `internal/pipeline` and marshalled to YAML, rather than
rendered from text templates.

**Rationale.** Type safety: the compiler catches structural mistakes, and the pipeline shape cannot drift from a
free-form template. It also makes golden testing straightforward. The cost is more Go code than a template, which is an
acceptable trade for correctness in a tool whose entire job is emitting valid YAML.

## 2. Schema generated by reflection (invopop), validated by santhosh-tekuri

**Decision.** The configuration JSON Schema is reflected from the config structs using `invopop/jsonschema` (in
`tools/schema`), and loaded configs are validated against it using `santhosh-tekuri/jsonschema/v6` (in
`internal/config`).

**Context.** The initial implementation hand-wrote the schema as Go maps. Jonathan asked whether a library could reduce
that hand-written code.

**Rationale.** `santhosh-tekuri/jsonschema/v6` only _validates_; it cannot generate a schema from structs. `invopop`
_generates_ but does not validate. Using both — each for its strength — removed ~200 lines of hand-written schema and
guarantees the schema tracks the structs, while keeping runtime validation. As a bonus, the two independent
implementations cross-check each other (the validator compiles the generator's output against the JSON Schema
meta-schema).

## 3. Schema written to two files with a drift guard

**Decision.** `task go:schema` writes both the canonical `schemas/aur-pipelines.json` (published, referenced by editors)
and an embedded copy at `internal/config/schema/aur-pipelines.json`; a test asserts they are identical.

**Rationale.** `go:embed` cannot reach outside a package's directory, so the runtime validator needs a copy inside
`internal/config`. Generating both from one run plus a byte-identity test means they can never silently diverge.

## 4. Validate the raw parsed document, not the decoded struct

**Decision.** `internal/config` validates `viper.AllSettings()` (the raw parsed YAML) against the schema, before
decoding into the `Config` struct.

**Rationale.** Struct decoding (mapstructure) silently drops unknown keys, so validating the decoded struct would make
`additionalProperties: false` useless — typos and stray keys would pass. Validating the raw document reports unknown
keys, missing required fields, and bad enum/pattern values against what the user actually wrote. Defaults are applied
_after_ validation so the loaded config is always fully populated.

## 5. Golden tests compare semantically, not byte-for-byte

**Decision.** Schema and generator golden tests parse both the generated output and the committed file and compare the
structures, rather than comparing raw bytes.

**Context.** A byte-for-byte comparison failed intermittently and looked like a stale-build or coverage problem.

**Rationale.** Prettier reformats the committed JSON/YAML during `task lint` (for example compacting short arrays onto
one line), which `json.MarshalIndent` never produces. A byte comparison therefore fails after any lint run. Semantic
comparison is robust to formatting while still catching real content changes.

## 6. RPC as the primary dependency-resolution source

**Decision.** The resolver's default `Source` is `RPCSource` (the AUR RPC v5 `info` endpoint), not the git/`.SRCINFO`
path.

**Context.** The original plan (agreed as point 2=b) was to fetch dependency data by cloning each package's git
repository and parsing `.SRCINFO`, using RPC only for membership and `provides`.

**Rationale.** The RPC `info` endpoint returns everything the resolver needs — package base, all three dependency lists,
and `provides` — in a single batched call, which is dramatically more efficient than cloning every package. The
`.SRCINFO`/`GitFetcher` path remains implemented and available as an alternative `Source` if RPC metadata staleness ever
becomes a concern. **Revisitable** if stale RPC data proves a problem in practice.

**Known limitation.** A dependency satisfied purely by another AUR package's `provides` is only resolved when that
providing package is already in the fetched closure; resolving an otherwise-unreferenced provider would require an RPC
search-by-provides. Documented in the resolver package comment.

## 7. Concourse credential-manager references for all secrets

**Decision.** Generated pipelines never embed secret values; they use Concourse `((...))` credential references that
Concourse resolves against OpenBao at run time.

**Context.** The README originally described in-pipeline OpenBao AppRole authentication for the signing stage.

**Rationale.** `((...))` keeps secret values out of the config file, the generated pipelines, and Concourse's stored
pipeline definitions; it removes an entire class of in-pipeline auth code; and it delegates access control and auditing
to the credential manager. This is the idiomatic Concourse approach and is strictly better than in-pipeline auth.

## 8. Per-webhook and per-image secret paths

**Decision.** Each webhook is configured with a `secret` name that resolves to `((webhooks/<secret>.url))`; each
container image has an optional `secret` resolving to `((repositories/<secret>.username))` and `.password`.

**Context.** An earlier version hardcoded a single `((webhook.url))`, which limited the tool to one webhook endpoint;
and container images could not be pulled from private registries.

**Rationale.** A named secret per webhook/image lets each have its own dedicated credential (with room for future fields
such as authentication tokens), keeps endpoints and credentials entirely out of the configuration, and lets multiple
distinct endpoints be configured. Secret names are pattern-constrained so they cannot produce malformed references.

## 9. Notification templating via shell `${VAR}` expansion at run time

**Decision.** Webhook header values and body templates use shell-style `${VAR}` references, expanded by the notification
task at run time. The task exports `PACKAGE_NAME`, `PACKAGE_VERSION`, `PIPELINE_STATUS`, `PIPELINE_URL` (and
`REPOSITORY` for cleanup).

**Context.** The first implementation used Go-template syntax (`{{ .PackageName }}`) and assumed Concourse would render
it. In production the tokens came through as literal text.

**Rationale.** Concourse performs no Go-template rendering — its only interpolation is `((...))` credential lookups.
Nothing was substituting the template variables. Shell `${VAR}` expansion needs no template engine: the task exports the
values and the shell expands them. Templates are passed to the task as **params** (not interpolated into the script
body), which also avoids a YAML-formatting problem (see decision 11).

## 10. `type` + `when` webhook selection (no conditional templating)

**Decision.** Each webhook entry declares a `type` (`build`/`cleanup`) and `when` (`on_success`/`on_failure`); the
generator attaches matching webhooks to the corresponding job hook.

**Rationale.** Because a distinct webhook is configured per outcome, each message applies to exactly one outcome, which
removes the need for any conditional logic inside templates. It also cleanly supports different messages (and different
endpoints) for success versus failure, build versus cleanup.

## 11. Best-effort, block-readable notification scripts

**Decision.** The notify script uses `set -u` only (not `-e`/`pipefail`), and each `curl` is guarded with `|| true`.
Templates are passed as env-var params rather than interpolated into the script body.

**Rationale (best-effort).** A notification is a side channel; one unreachable endpoint must not abort the others or
fail the build's notification hook (which could obscure the real result). `--fail` is kept so genuine failures remain
visible in the logs.

**Rationale (params, not inline).** `go.yaml.in/yaml/v3` only emits a readable `|-` block scalar when no line has
trailing whitespace. User templates commonly contain trailing whitespace, which would force the whole script into an
escaped single-line scalar. Keeping user content in params leaves the generated script clean and readable.

## 12. Per-pipeline topology with race-safe cross-pipeline ordering

**Decision.** Each package base gets its own pipeline with `build-upload` → `sign` → `repository` (serial) jobs. A
dependent package's build is triggered by the shared repository-database resource, not by the raw package upload.

**Context.** We considered a single job with sequential tasks, aggregate global sign/repository pipelines, and other
shapes before settling here.

**Rationale.** Per-pipeline keeps each package self-contained and its jobs chainable via `passed:`. Triggering
dependents on the repository database (which only changes after the serial repository job runs `repo-add`) guarantees a
dependency is actually installable before a dependent builds against it — avoiding a race that triggering on the raw
upload would introduce. `passed:` and `serial_groups` are within-pipeline only, so cross-pipeline ordering is
necessarily resource-version-based.

## 13. All container images optional with defaults

**Decision.** Every `container` stage (and the whole block) is optional; omitted stages fall back to built-in defaults
applied at load time.

**Rationale.** A minimal config need only specify `bucket` and `packages`. Defaults are applied in the loader so the
rest of the code always sees a fully populated config, and the generated pipeline shows concrete images. The cleanup
default (`amazon/aws-cli`) is chosen because that job needs the AWS CLI for S3-compatible R2 access.

## 14. Build metadata via a metadata resource (not task env vars)

**Decision.** `${PIPELINE_URL}` is built from files written by a `metadata` resource (`swce/metadata-resource`), which
each notification-carrying job fetches; the notify task reads `meta/atc-external-url`, `meta/build-team-name`, etc.

**Context.** The first implementation built the URL from `${ATC_EXTERNAL_URL}` and `${BUILD_*}` environment variables.
In production the cleanup notification aborted with `sh: BUILD_TEAM_NAME: parameter not set`.

**Rationale.** Concourse deliberately does **not** expose build metadata to task environments — the maintainers consider
it an anti-pattern, and the PR to expose even `ATC_EXTERNAL_URL` to tasks is still unmerged (confirmed against the
latest release). The established pattern the maintainers point to is a resource that writes the metadata to files a task
can read. Under `set -u`, referencing the unset variables aborted the script; sourcing from the metadata resource both
fixes the crash and produces a real URL. Each metadata read is additionally guarded (`|| true`) so a missing file yields
an empty value rather than aborting. The `metadata` resource is only added when notifications are configured.
